# The ship loop: one pass over all ships

Date: 2026-11-20. Script: `scripts/investigations/2026-11-20-ship-loop/ship_hash.py`.

## Result

A tick with ship traffic on Kattegat (2000 animals, 5,148 ships, about 250 of them deterring
in any tick) takes about 34 ms where it took about 88 ms: 2.6 times faster. Results are
identical to the last bit.

| Kattegat with ships, days 1-2, seed 42 | Before | After |
|---|---|---|
| Time per tick | 87.8 ms (127.5 ms in a second, busier run) | 33.7 ms, 34.4 ms |
| of which ship deterrence | 76.1 ms (88.5 ms) | 26.3 ms, 27.0 ms |
| Fingerprint of deterrence vectors and final state | `16fefe5440066e4f` | `16fefe5440066e4f` |

"Before" is commit `942cd02`. Runs were alternated on a shared machine; the first "before"
run coincided with other load and is given in brackets.

## What was changed

- **One pass instead of a loop over ships.** The deterrence calculation handled each ship
  separately, with some forty small NumPy calls per ship. It now lays out the
  (ship, animal, sub-step) pairs of all ships in one set of arrays, in the order the loop
  visited them, and does each step once: distances, sound level, reaction, vector. Every
  number comes from the same elementwise operation as before.
- **Loudest ship per animal and sub-step.** The loop kept the loudest ship seen so far, so
  among equally loud ships the lowest id won. The pass sorts the pairs by animal and
  sub-step, then loudness, then position in ship order, and takes the first of each group:
  the same winner.
- **In-range pairs in compiled code.** Finding the pairs within range was the largest part
  of the pass (about 28 ms of 45). A compiled loop now does it in about 1.5 ms. The NumPy
  form is kept as the reference and as the fallback without Numba; a test checks the two
  return exactly the same arrays.
- **Ships waiting at a buoy.** Each of the 5,148 ships was fully updated every tick. A ship
  that is waiting, and will still be waiting after the tick, now only counts down. A test
  checks the ship's state against the full update at every tick.
- **Pre-cull.** Which animals can be in range of a ship is decided on squared distances for
  all ships at once, with one metre of margin so that rounding can only keep an animal too
  many, which changes nothing.

## What is left

After the change a tick spends about 27 ms on ship deterrence: sound propagation about 8 ms
(compiled, one element at a time), the reaction draws about 7 ms (one random stream per ship
and tick, by design), the rest in array handling.

- **Sound propagation in parallel** would be bit-identical and could save most of its 8 ms.
  It was not done: on this shared machine parallel kernels were slower than serial ones for
  the reference-memory kernels (`2026-11-20-tick-profile.md`).
- **One random stream per tick instead of per ship** would remove most of the draw cost but
  changes which animals react, so seeded ship results would change.
